# Pangolin CPU kernel log

Running log of CPU kernel design, implementation choices, and benchmark results
for the planar (`gptq_p`) Pangolin GEMV kernel on host x86-64.

## Hardware / software snapshot

- Host: x86_64 AVX-512 capable CPU (Xeon Platinum 8559C)
- CPU flags include: `avx512f`, `avx512bw`, `avx512vl`, `avx512_bf16`, `avx512_vnni`, `avx_vnni`
- AMX (tile) support: **not present** on this host (no `amx_tile`, `amx_int8`, or `amx_bf16` flags)
- Torch 2.13.0+cpu, Python 3.12.8
- JIT compiled via `gptqmodel_pangolin_cpu_ops` with `-fopenmp` on Linux

## Design

### Decode philosophy

The CPU has far less memory bandwidth and much higher latency than a GPU, but
many cores and large caches. The kernel therefore:

1. **Avoids materializing dense weights.** Packed planar words are read once per
   32-code block and decoded on-the-fly inside the same hot loop that computes
   the GEMV. This keeps the weight working set at `bits/16` of a dense fp16
   matrix.
2. **Uses all available cores.** Output columns are parallelized with
   `at::parallel_for`; each thread works on independent column chunks. SIMD
   kernels are kept free of `at::parallel_for` to avoid OpenMP target-attribute
   interaction issues; the parallel wrapper calls targeted per-column functions.
3. **Wide SIMD to amortize memory latency.** AVX-512 (16 lanes) is used for the
   decode-dominant decode shapes (`M <= 8`); AVX2 (8 lanes) is the fallback for
   larger `M` where register pressure would otherwise spill. A scalar fallback
   covers any remaining shapes.
4. **Precomputes `zero * scale` per group-column.** This moves the zero-point
   decode out of the hot loop; the inner loop only loads `scale`, `zero_scale`,
   the packed `qweight` words, and the broadcast activation.
5. **BF16 I/O with FP32 accumulation.** The public API and the C++ kernel accept
   BF16 input and produce BF16 output. Internal math (scale/zero/accumulator)
   stays in FP32 for numerical stability; the final FP32 accumulators are cast
   to BF16 at store time.

### Planar decode

Bit layouts per 32-code block (`bits` int32 words, low plane first):

- 3-bit = 2-word plane + 1-word plane
- 5-bit = 4-word plane + 1-word plane
- 6-bit = 4-word plane + 2-word plane
- 7-bit = 4-word plane + 2-word plane + 1-word plane

For each 32-code block the kernel loads the `bits` packed words once per column
vector, then for each `k` in the block it shifts/masks/ORs the appropriate
plane word into a full integer code, converts to float, and performs
`weight = code * scale - zero_scale`. The activation is then broadcast and
fused with `vfmadd`.

### Implementation dispatch

- AVX-512 is selected when `N % 16 == 0` and `M <= 8`.
- AVX2 is selected when `N % 8 == 0`.
- A scalar fallback covers any remaining shapes.

`M = 16` and `M = 32` are routed through AVX2 to avoid the heavy ZMM register
spills that the AVX-512 current GCC target prologues produce.

### Notes and future work

- SIMD tail coverage: the vector kernels compute `N / VLEN` full chunks and rely
  on `N % 32 == 0` being enforced in `pangolin_gemv_cpu`. Any future relaxation
  of that padding requirement would need an explicit scalar tail loop.
- OpenMP runtime: `-fopenmp` is required for `at::parallel_for` to use multiple
  threads, and it links libgomp on Linux. PyTorch wheels that link Intel's
  libiomp5 instead can end up with two OpenMP runtimes in the same process,
  which is a known source of oversubscription or hangs; monitor on non-libgomp
  wheels.
- `zero * scale` is decoded and precomputed per call. For repeated token
  inference it could be cached per `(qzeros, scales, bits)` to remove the fixed
  `G*N` overhead.

### AMX / tile matrices

The host CPU does not expose AMX tile instructions, so no tile-based matmul
path is implemented or enabled. AVX-512 BF16/VNNI are present and could be used
for future BF16 conversion / dot-product micro-optimizations; the current path
uses standard AVX-512 FMA and scalar BF16 rounding.

## Benchmark methodology

- Reference: `TorchLinear.dequantize_weight()` followed by `torch.matmul` on CPU.
- Timed region: warmed, then repeated; `ms` values below are per-call averages.
- Thread count: 8 (same budget for kernel and reference).
- Batch/M sizes: decode-focused `M = 1, 2, 4, 8`.
- Input/output dtype: **bfloat16** for both the kernel and the reference matmul.
- Shape sets: Laguna S 2.1, GLM-4.5-Air (public proxy for GLM-4.5-Flash-0731),
  and DeepSeek-V4-Flash-0731 projection dimensions derived from public configs.
